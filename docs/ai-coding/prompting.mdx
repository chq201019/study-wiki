# 提示词工程：任务书与技巧

agent 模式下你不再是"提问者"，而是"派活的"：写一份**任务书**（目标 + 约束 + 验收标准），agent 自己读代码、改文件、跑编译、看报错、迭代到通过。**你的工作量从"搬运和盯梢"变成"写清楚 + 验收"**——这一页教的就是怎么写好这份任务书。

## 1. 任务书五件套

网页端聊天的"上下文公式"到了 agent 这里变成任务书结构——区别是：环境、报错这些信息 agent 可以**自己收集**，你只需要把"它自己查不到的东西"写明白：

```text
① 环境（一句话）：芯片/框架/版本——agent 能从工程里推断，但写死更稳
② 目标：要达成什么，一句话说死
③ 约束：不能动什么、必须用什么（"别动 sdkconfig""用 RMT 外设"）
④ 验收标准：怎样算"做完了"——可执行、可观察
⑤ 上下文入口：相关文件路径、参考文档、本站教程页
```

**④ 是任务书的灵魂**。没有验收标准的任务书，agent 只能"写完就算完"——它自我感觉良好地交付，你打开一看完全不是那回事。

### 验收标准怎么写：可执行、可观察

| | 写法 |
| --- | --- |
| ❌ 模糊 | "把串口调通" |
| ✅ 可验收 | "`idf.py build` 零警告通过；上电后 GPIO43 以 115200 输出 `boot ok`，每秒一行计数；拔掉 RX 不崩，重插恢复输出" |

再补三条通用写法：

- **以命令收尾**："`idf.py build` 零错误、`idf.py qemu monitor` 里单元测试全绿"——agent 能自己跑的验收，它会自己迭代到位
- **以观察收尾**："用逻辑分析仪量 GPIO4 输出 800kHz±10%"——需要硬件的验收 agent 做不了，写明"这条由我上机验收"
- **写明失败行为**："CRC 错误时打印 `crc fail` 并丢弃该帧，不得静默重试超过 3 次"

## 2. 好坏任务书对照：三个高频场景

### 场景 A：写一个驱动

**❌ 坏任务书**：

> 帮我写个 ESP32 读 DHT22 的程序

agent 会自由发挥：库随便挑、引脚随便定、错误处理随缘——然后你花半小时改成自己的需求。

**✅ 好任务书**：

> 环境：ESP32-S3 DevKitC-1，arduino-esp32 3.3.x（工程在当前目录）。
> 目标：GPIO5 读 DHT22，10 秒采一次，串口 9600 打印温度湿度。
> 约束：用官方 DHT sensor 库；不改动 platformio.ini 之外的现有文件。
> 验收：编译通过；串口每 10 秒输出 `T=xx.x H=xx.x`；传感器拔掉时输出明确错误不卡死。
> 参考：DHT22 数据手册在 docs/ 下。

### 场景 B：修一个 bug

**❌ 坏**："串口乱码帮我修修"——agent 可能重写整个 UART 层，顺带改掉三个无关文件。

**✅ 好**：

> 现象：串口输出乱码（完整乱码截图内容如下：……）。
> 我已确认：波特率两端都是 115200、接线 TX/RX 未反。
> 约束：只排查时钟配置相关代码，**不要改动应用逻辑**；每个假设先在回复里给出，动手前说明要改哪个文件哪几行。
> 验收：串口输出可读英文；`git diff` 只包含时钟相关改动。

"git diff 只包含……"这一条是 agent 时代的防走神器——**约束它的改动范围，验收时 diff 一眼可查**。

### 场景 C：批量机械修改

agent 最擅长的活之一，任务书反而要写得更死：

> 把仓库里所有 `ledcSetup/ledcAttachPin` 旧 API 调用迁移到 arduino-esp32 3.x 的 `ledcAttach`（对照 [api-map](../reference/api-map) 的映射表）。
> 约束：只改这三种函数的调用与参数顺序，不改任何逻辑；每改一处跑一次编译。
> 验收：全仓库 grep 不到旧函数名；编译零错误零新增警告；`git diff` 逐条列给我。

## 3. 提示词工程技巧包

任务书是骨架，这一节是往里填的肌肉——五个立刻能用的技巧，每个附嵌入式场景示例。

### 技巧一：给角色，给视角

开场一句"你是谁"，回答的专业度立刻不同：

> 你是熟悉 ESP-IDF 5.5 的嵌入式工程师，正在 review 一名两年经验开发者的代码。

角色提示的真实作用是**划定语料范围**：说"嵌入式工程师"会激活内存约束、中断安全这类关注点；说"评审"会激活挑错模式而不是夸奖模式。让 agent 排查问题时加一句"假设问题出在我没想到的地方"，能有效打破顺着你的思路走。

### 技巧二：few-shot——给例子比给描述准

说十遍"按我的风格写注释"，不如直接贴一个范例：

> 我项目的驱动函数都长这样（示例）：
> ```c
> /// 初始化 SHT40，失败返回 NULL（打日志 err_init_sht40）
> sht40_t *sht40_init(i2c_port_t port);
> ```
> 按同样的注释风格和错误处理模式，给 BMP390 写初始化。

这招对"风格对齐"类任务几乎必胜：**命名习惯、注释密度、错误码用法，全部从例子里抄**，比任何文字描述都精确。嵌入式项目尤其值钱——寄存器操作套路、日志格式这类"团队方言"，例子一贴 agent 就懂。

### 技巧三：约束输出格式

你需要什么形态的产出，就在提示词里定义死：

> 输出格式要求：
> 1. 先给"改动方案"三行以内，我确认后你再动手
> 2. 代码只给新增/修改的 diff，不要整文件重贴
> 3. 涉及寄存器/命令字时在行尾注释标注手册出处
> 4. 不确定的参数一律标 `TODO(待查手册)`，禁止猜

这是控制 agent 的缰绳：**"先方案后动手"防止它上来就改文件；"只给 diff"防止上下文爆炸；"不确定就标 TODO"直接掐断幻觉的产出通道**（比事后核对省力得多——不让它写错，好过写错了再改）。

### 技巧四：分步引导，别一口气要结果

复杂任务把"思考过程"显式编入提示词：

> 按顺序回答，每步单独一段：
> ① 这个任务涉及哪些文件和哪些外设？
> ② 有哪些备选实现路径，各自代价？
> ③ 你推荐哪条，为什么？
> ④ 我确认后再出代码。

价值在 ①②——**它逼 agent 先盘点资源再动手**，你也在写代码之前拿到了否决机会。流程敏感的活（改启动流程、动分区表）尤其要先走这三步。

### 技巧五：负面清单——说"不要什么"

agent 对"不要做 X"的遵守度出乎意料地好，把你的雷区直接列出来：

> 不要：改 sdkconfig；引入新依赖；用 C++ 特性（本工程是纯 C）；在 ISR 里加打印；重排 include 顺序。

负面清单和[工作流页](./workflow)的 `AGENTS.md` 是配套的：**项目级雷区固化进 AGENTS.md（每任务自动生效），任务级雷区写进任务书**——两层叠加后，agent 的"自由发挥空间"被压到很小。

### 模板复用：好提示词要攒

每次写完一份效果好的任务书，**回填进你的模板库**（仓库里建 `prompts/` 目录或笔记）。攒到十几条后你会发现：80% 的任务变成了"改两三个参数的填空题"——这才是提示词工程在 agent 时代的最终形态：**提示词本身成为项目资产**。

## 4. 验收与返工：你的出口话术

agent 自己跑完"编译通过"不等于交付。**验收三步**：

1. **看 diff，不看总结**。agent 的"我已完成……"是自我报告，`git diff` 才是事实。逐行过一遍，看不懂的行让它解释——解释不清的行就是最大的嫌疑
2. **核对验收标准逐条打勾**。任务书里写了几条验收，就验几条，尤其"失败行为"那条（agent 最爱跳过错误路径）
3. **上机验证**。编译和单元测试 agent 能自己跑，引脚波形、电流、真实传感器响应必须你来

**返工话术**（发现不对时）：

- "验收标准第 2 条不满足：传感器拔掉时它卡死了。修复，别动其他文件"——**引用具体条目**，而不是"不对，重写"
- "这个改动为什么动了 xxx.c？任务书没要求。回滚这个文件的改动"——范围走查
- "停下来。现在的方向偏离了任务书，我们回到原始目标重新对齐"——agent 连续三轮没收敛时果断喊停，git 回到上一个提交点（这就是为什么[工作流页](./workflow)要求小步提交）

:::caution[警惕 agent 的"自我确认"]
agent 有一类顽固行为：用一个错误的假设自我验证到底（比如坚持"传感器地址是 0x77"），每轮"修复"都在错误假设上叠补丁。**发现它连续两轮引用同一个未经验证的假设时，打断它**："先做实验区分假设 A 和 B，再动手改"——把科学方法强行注入它的循环。
:::

## 5. 学习场景专用：让 agent 当陪练而不是枪手

正在跟本站教程的读者，几个特别划算的用法（这些是网页端和 agent 都能做的）：

- **费曼检验**："我刚学完[GPIO 上拉下拉](../course/l4-peripherals/gpio)这节，听我讲一遍，指出理解错误的地方"
- **出题**："针对 I2C 字节级时序出 5 道有陷阱的选择题，答完再对答案"
- **陪练模式（agent 独有优势）**：练习仓库里下任务书——"我打算自己写 GPIO 初始化，你只在我写完后 review，**不许替我写**；我卡住 10 分钟以上再提示"——把"不许替我写"写进任务书，agent 是最好的陪练而不是枪手
- **迁移练习**："把这段 Arduino 代码改写成 IDF 原生 API，逐行解释差异"——配合[速查表 API 对照](../reference/api-map)自查

**红线**：让 agent 直接替你写教程练习的完整答案。跳过的思考过程会在下一次"没有 AI 的考场"（比赛现场、面试白板、设备现场）连本带利讨回来。

## 常见坑

| 坑 | 解法 |
| --- | --- |
| 任务书没有验收标准 | 每份任务书至少一条"agent 可自验"+ 一条"人机共验" |
| 验收看 agent 的总结不看 diff | 永远逐行看 `git diff` |
| 不约束改动范围 | 任务书里写死"git diff 只包含×××" |
| agent 连续返工不收敛 | 三个返工话术轮着用；三轮无果就回 git 重来 |
| 把上机验收也交给 agent | 它没有你的硬件；波形/电流/真机响应必须人验 |
| 学习期让它全包 | 任务书写明"不许替我写"的陪练条款 |
