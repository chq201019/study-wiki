# 交付自检清单

提交前照着下面逐项打勾。任何一项没过，先修再交。

## 通用（两条路线都要过）

### 硬件

- [ ] 所有模块单独通电正常（逐个拔插测，不要整体测完就假设每个都好）
- [ ] 供电充足：满负载（WiFi + 电机/舵机 + 屏幕）连续运行 30 分钟不复位
- [ ] 接线牢固：杜邦线没有虚接，面包板没有氧化发绿的接触点
- [ ] 没用任何被禁用的引脚（35/36/37 绝对不能碰）
- [ ] 板子固定住了，展示时不会滑落、不会拉断线

### 功能

- [ ] **冷启动**正常：断电 10 秒再上电，功能完整（不要只测热重启）
- [ ] 连续运行 1 小时无崩溃（挂串口日志，全程看）
- [ ] 所有赛题需求逐条对照验证过（拿需求清单一条一条打勾，不是凭印象）
- [ ] 异常场景有兜底：传感器掉线、网络断开、MQTT 断连都能恢复
- [ ] 断电重启后配置还在（WiFi 信息没有每次都要重配）

### 软件

- [ ] 串口日志里没有 `Guru Meditation` / `panic` / `abort`
- [ ] 没有硬编码的 WiFi 密码、账号、密钥在代码里明文
- [ ] 提交的是**完整工程**，不是只有 `.ino` 的片段（Arduino 里要包含所有引用的库或说明）
- [ ] 代码里没有 `delay(5000)` 这种会卡住整个程序的写法
- [ ] 版本号、作者、日期写在文件头部注释里

### 交付物

- [ ] 源代码（工程目录，能在干净环境编译通过）
- [ ] 预编译固件 `.bin`（至少 app 一份，OTA 项目要两个）
- [ ] 原理图 / 接线图（评委要看）
- [ ] 系统框图
- [ ] 说明文档：功能列表、硬件清单、操作说明、如何编译烧录
- [ ] 演示视频（兜底）

## 现场制作版追加

- [ ] 赛前已经**完整跑通一遍全部评分项**（不是只测了各个模块）
- [ ] 现场用的代码就是赛前验证过的版本，只准备了配置文件改动点
- [ ] 提前到场，用现场的真实网络完整跑一遍
- [ ] 确认了现场的网络：SSID、密码、是否隔离、能不能访问外网
- [ ] 带了备用板子、备用传感器、备用线
- [ ] 带了 U 盘：固件 + 源码 + 文档 + 视频
- [ ] 演示流程能在 3 分钟内讲完

## 提前提交版追加

- [ ] 提交截止日前**一周**功能已冻结，剩余时间只做验证和材料
- [ ] 说明文档达到"照着就能跑"的程度：每一步操作、每个依赖都写清
- [ ] 演示视频拍清楚每一个评分项，和需求清单一一对应
- [ ] 找一个没参与过项目的同学，只拿提交材料试着把作品跑起来
- [ ] 评委可能问的问题（方案、指标测量、踩坑）写进了文档而不是只靠答辩

## 最后：答辩四个必问

| 问题 | 准备要点 |
| --- | --- |
| 「为什么用这个方案？」 | 说清约束（算力、功耗、时限、评分项）如何推导到方案，不要只说"因为简单" |
| 「这个指标怎么测的？」 | 说清测量方法和数据来源。评委最看重可信度 |
| 「遇到的最大问题是什么？」 | 准备一个真实的排障故事（有数据、有结论），比"没遇到问题"好得多 |
| 「还能怎么改进？」 | 说出 1～2 个真实的改进方向（精度、功耗、成本、扩展性），体现你想过 |

:::tip[一个反常识的建议]
把调试过程和踩过的坑**主动讲出来**。评委见过太多"一次就做出来"的项目，真实工程里的排障能力恰恰是评分点。做不出来的东西要说清楚为什么做不出来、试过什么。
:::
