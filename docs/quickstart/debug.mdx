# QS-5 串口与调试

**时长 40 分钟 · 产出：会看日志，出问题知道从哪查**

:::tip[串口波特率]
所有示例程序里的串口都初始化成 9600（米思齐的默认值）。
在米思齐里点开串口窗口，把右下角的波特率也选成 `9600`，两边不一致串口就是乱码。
:::

调试的核心就一句话：**让板子把"我在干嘛"打出来**。板子不会说话，串口打印就是它的嘴。

## 串口基础

打印内容就一种积木：「串口」分类里的 **Serial 打印**（自动换行 / 不换行两种）：

```text
Serial 打印 自动换行 "带换行"
Serial 打印 不换行 <拼接积木咬个读数进去>     ← 想打变量就用「文本」分类的拼接积木
延时 1000 毫秒
```

两个使用习惯，比任何高级工具都值钱：

1. **每加一个功能，就加一行打印**——正常运行时能看到板子在干嘛，出问题时能看出停在哪
2. **变量值包在文本里打**，比如 `"温度: " + 温度`，光打一个数字回头自己都忘了是什么

## 标记打印法：定位"跑到一半就不动"

程序卡死了，不要从头看。在怀疑的位置前后各塞一块打印：

```text
Serial 打印 自动换行 ">>> 进入 initWifi"
<initWifi 那段积木>
Serial 打印 自动换行 ">>> initWifi 完成，进入 connect"
<connect 那段积木>
Serial 打印 自动换行 ">>> connect 完成"
```

看最后打印到哪一行，问题就在下一行。比赛现场这招能救命。

## 启动日志速查

按 RST 后第一行永远是 `rst:0xX (原因),boot:0xY (模式)`。注意 **S3 的码表和经典 ESP32 不一样**，网上老教程按 ESP32 解释的会对不上号。

| `rst:` | 含义 | 排查方向 |
| --- | --- | --- |
| `0x1` | 上电复位（POWERON） | 正常 |
| `0x3` | 软件复位（RTC_SW_SYS_RST） | 看代码里有没有 `esp_restart()` |
| `0x5` | 深睡唤醒（DEEPSLEEP） | 用过深度睡眠才会出现 |
| `0x7` / `0x8` / `0xb` | 主看门狗复位（MWDT） | 程序里有死循环卡住了主循环 |
| `0x9` / `0x10` | RTC 看门狗复位（RTC_WDT） | 同上，多半是任务卡死没喂狗 |
| `0xf` | **欠压复位（BROWN_OUT）** | 供电不足，换线/换电源，别接扩展坞 |
| `0x15` / `0x16` | USB 复位（USB_UART / USB_JTAG） | 插拔了 USB 线，或用了 USB 口的串口/JTAG |
| `0x17` | 电源毛刺（PWR_GLITCH） | 电源不稳，检查供电 |

:::warning[`0x1` 有三种含义，别一看到就放过]
`0x1` 既是**上电复位**，也可能是**芯片级欠压**或**超级看门狗**。如果板子反复重启但每次都是 `rst:0x1`，先按供电问题查，别默认它是正常上电。
:::

`boot:0x8`、`boot:0x13`、`boot:0x33` 这类都是正常的 SPI Flash 启动模式（数值随引脚电平组合变），后面跟着 `SPI_FAST_FLASH_BOOT` 就不用管。

> **进下载模式不靠看 `rst:` 认**。判断板子在不在下载模式，看 `boot:` 后面跟的是不是 `DOWNLOAD_BOOT`；`rst:0x15` 只是说这次是 USB 触发的复位。完整的码表见[错误码速查](../reference/error-codes)。
