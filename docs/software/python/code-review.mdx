# 代码审查与协作

**本课目标**：让代码审查真正提升质量，而不是变成形式或摩擦。

## 审查该看什么

:::tip[按优先级排序]
**第一优先级（必须指出）**：

- **正确性**：逻辑错、边界漏、并发问题
- **安全问题**：注入、越权、密钥泄露
- **资源泄漏**：没关文件/连接/锁
- **数据损坏风险**：非原子写、缺事务

**第二优先级（建议）**：

- 可读性、命名
- 重复代码
- 测试覆盖

**不该管的**：

- **纯风格**（交给格式化工具）
- 个人偏好（"我更喜欢另一种写法"）
:::

:::danger[用工具做的事不要靠人]
**格式、import 顺序、行长度** —— 这些应该由 `black`/`clang-format`/`ruff` 自动处理，**不该出现在审查意见里**。

**否则审查的注意力全被消耗在无意义的争论上。**
:::

## 有效的审查意见

:::tip[三个特征]
1. **具体**：指出哪一行、什么问题
2. **解释为什么**：不只是"这样不好"
3. **给建议或提问**：而不是命令
:::

| 差的意见 | 好的意见 |
| --- | --- |
| 这里有问题 | `buf` 只有 16 字节，但 `strcpy` 的来源可能更长，会溢出 |
| 不要这么写 | 这里在循环里做 `+=` 字符串拼接，复杂度是 O(n²)，建议用 `join` |
| 改成 XXX | 如果这里换成 `join` 会不会更快？我不确定数据量大小 |

:::warning[用提问代替断言，能减少防御心理]
**"这里是不是漏了空指针检查？"** 比 **"你忘了空指针检查"** 更容易被接受。

**但涉及安全/数据损坏时，要直接明确，不要用模糊的提问。**
:::

## 审查清单

:::info[一份可直接用的清单]
**通用**：

- [ ] 有没有硬编码的密钥/路径/地址
- [ ] 错误路径有没有处理（不只是 happy path）
- [ ] 日志里有没有敏感信息
- [ ] 有没有引入不必要的依赖

**C/C++**：

- [ ] 所有 `malloc` 有对应的 `free`（含错误路径）
- [ ] 缓冲区长度检查了吗
- [ ] 有符号/无符号比较
- [ ] 返回值和 `errno` 检查

**并发**：

- [ ] 共享数据有保护吗
- [ ] 锁的获取顺序一致吗（防死锁）
- [ ] 临界区里有没有阻塞调用

**数据库**：

- [ ] 多步操作在事务里吗
- [ ] 有没有 N+1 查询
- [ ] 索引够不够
:::

## PR 该多大

:::danger[超过 400 行的 PR 审查质量断崖下降]
**研究结论**：400 行以内能找到多数问题，超过 1000 行基本只剩"看起来还行"。

**建议**：

- **单个 PR 控制在 200~400 行**
- 大改动**拆成多个 PR**（按功能切片，而不是按文件）
- **重构和功能改动分开**（混在一起无法判断行为变化）
:::

:::warning["顺便改"是 PR 变大的主因]
**"我看到这里有个 typo 就改了"、格式化了整个文件、"顺手升了依赖"** —— 这些都会让 diff 失控。

**规矩**：**PR 只做一件事**。其他改动另开 PR。
:::

## 五个让 PR 卡住的原因

:::danger[① 描述太简略]
```text
标题：fix bug
描述：（空）
```

**审查者得靠猜** —— 他不知道为什么要改，就只好反复问。

**至少要写**：改了什么问题、怎么验证的。
:::

:::danger[② 混入了无关改动]
**格式化整个文件、改了不相关的模块** —— diff 里 80% 是噪音，真正的改动找不出来。
:::

:::danger[③ 没有测试或验证说明]
**"我本地试过了"不够** —— 要说清试了什么场景、边界情况。
:::

:::danger[④ CI 挂了]
**审查者看到红色就不想看了。**

**提交前先本地跑一遍 CI 等价检查**。
:::

:::danger[⑤ 评论没回应]
**每条评论要么改、要么解释为什么不改。**

**沉默会让审查者以为被无视。**
:::

## 接受审查的心态

:::tip[四条实用建议]
1. **代码被批评 ≠ 你被批评**
2. **不明就问**：如果意见不清楚，直接问，别猜
3. **不同意可以说**：给理由，达成共识比默认服从好
4. **感谢具体的人**：指出真问题的人值得谢谢
:::

:::warning[不要长期"我先改完再看"]
**如果一条意见需要大改，先回复"我需要重写这部分，明天再看"** —— 而不是沉默几小时。
:::

## 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 审查流于形式 | PR 太大 | 控制 400 行内 |
| 争论风格 | 没配格式化工具 | 用工具自动处理 |
| 意见被无视 | 没明确要求回应 | 约定"每条都要回复" |
| 反复来回 | 描述不清 | 写清楚问题与验证方式 |
| 上线出问题 | 只测 happy path | 审查清单强制检查错误路径 |
| 团队摩擦 | 措辞生硬 | 用提问代替断言 |

:::danger[审查发现不了的问题类型]
**代码审查对以下问题几乎无效**：

- **性能问题**（需要 profiling，不是读代码）
- **分布式竞态**（需要压测）
- **需求理解错误**（审查者不知道真实需求）
- **架构层面的问题**（单个 PR 看不出）

**这些要靠测试、监控、设计评审来解决。**
:::

- [ ] 能写出"具体+解释+建议"的审查意见

- [ ] 能说出 PR 卡住的五个原因
- [ ] **知道代码审查对性能/分布式竞态/需求错误无效**
