# Python 性能剖析与优化

**本课目标**：能找到真正的瓶颈，知道优化到什么程度就该停。

## 先测量，别猜

:::danger["我觉得这里慢"通常是错的]
**在 Python 里，真正慢的往往是**：

- 嵌套循环里的属性查找
- 反复创建临时对象
- 字符串拼接
- 数据库的 N+1 查询
- 序列化/反序列化

**而不是你直觉上觉得"算法复杂"的那部分。**
:::

## `cProfile`：函数级剖析

```python
import cProfile
import pstats

cProfile.run("main()", "prof.out")

p = pstats.Stats("prof.out")
p.sort_stats("cumulative").print_stats(20)     # 按累计耗时排序
```

**输出关键列**：

```text
ncalls  tottime  percall  cumtime  percall filename:lineno(function)
  1000    0.850    0.001    2.310    0.002 mymod.py:42(process)
   200    1.200    0.006    1.200    0.006 mymod.py:88(query_db)
```

| 列 | 含义 |
| --- | --- |
| `ncalls` | 调用次数 |
| **`tottime`** | **在本函数内部花的时间（不含子调用）** |
| `cumtime` | 含子调用的总时间 |
| `percall` | 每次平均 |

:::tip[先看 `tottime` 再看 `cumtime`]
- **`tottime` 高** = 这个函数自己就是热点（值得优化内部）
- **`cumtime` 高但 `tottime` 低** = 它只是在等子调用（应该往下钻）

**很多人只按 `cumtime` 排序然后优化了 `main`** —— 那是没有意义的。

```python
p.sort_stats("tottime").print_stats(20)      # 先看这个
```
:::

:::warning[`cProfile` 本身有开销]
它会拦截每次函数调用，**会显著放慢程序**（通常 2~5 倍），而且**偏向于"调用次数多"的函数**（因为每次调用都记一笔）。

**这只影响"相对比例"，不影响"谁是热点"的结论**（大体上）。

**要更精确的采样式剖析**，用 `py-spy`（不用改代码、开销低）：

```bash
pip install py-spy
py-spy record -o profile.svg -- python main.py
py-spy top -- python main.py
```

**`py-spy` 能直接生成火焰图，而且能 attach 到线上进程。**
:::

## `timeit`：微基准

```python
import timeit

# 单条语句
t = timeit.timeit("sum(range(100))", number=10000)
print(f"{t/10000*1e6:.2f} us/次")

# 比较两个写法
setup = "data = list(range(1000))"
print("循环:", timeit.timeit("out=[]\nfor x in data: out.append(x*2)", setup, number=1000))
print("推导:", timeit.timeit("out=[x*2 for x in data]", setup, number=1000))
```

:::danger[`timeit` 的五个使用要点]
**① 一定要指定 `number`，并且足够大**（否则被计时器精度淹没）

**② 把 setup 抽出来**（不要把它算进被测时间）

**③ 结果要有实际差异才算数** —— 5% 以内的差异在不同机器/版本上会反转

**④ 别在 `timeit` 里做 IO**（磁盘缓存会让第二次飞快）

**⑤ 用 `-m timeit` 在命令行跑最省事**

```bash
python -m timeit -s "data=list(range(1000))" "[x*2 for x in data]"
```
:::

## 常见优化手段的收益顺序

:::info[按"收益/成本"排序]
| 手段 | 典型收益 | 代价 |
| --- | --- | --- |
| **① 改算法/数据结构** | **10~1000 倍** | 要思考 |
| ② 消除 N+1 查询 | 10~100 倍 | 改 SQL |
| ③ 加缓存（`functools.lru_cache`） | 2~100 倍 | 内存 |
| ④ 用 `numpy` 等 C 扩展向量化 | **10~100 倍** | 学 API |
| ⑤ 换内置函数（`sum`/`join`/`map`） | 1.5~5 倍 | 几乎无 |
| ⑥ 局部变量代替属性访问 | 1.2~2 倍 | 可读性下降 |
| ⑦ 多进程（CPU 密集） | 接近核数 | 内存、复杂度 |

**注意第 ⑦ 项在最后** —— 因为如果算法本身是 O(n²)，加 8 个核也只是快 8 倍，而改算法能快 1000 倍。
:::

:::danger[最常见的三个"伪优化"]
**① 用 `while` 代替 `for`** —— 几乎总是更慢（`for` 走的是 C 层迭代协议）

**② 手动展开循环** —— Python 里循环体越少越好，展开反而增加字节码

**③ 预先分配 list 再赋值**
```python
out = [0] * n
for i in range(n):
    out[i] = f(i)          # ❌ 比 append 慢
```
```python
out = [f(i) for i in range(n)]    # ✅ 推导式最快
```
:::

## 缓存：最省事的加速

```python
from functools import lru_cache

@lru_cache(maxsize=1024)
def expensive(n):
    ...
```

:::warning[`lru_cache` 的三个前提]
1. **参数必须可哈希**（list/dict 不行）
2. **函数必须是纯的**（同样输入永远同样输出）
3. **要防止无界增长**（`maxsize=None` 会无限增长，记得设上限）

**如果参数是可变对象，可以用 `cache` 前先转成 tuple/frozenset。**
:::

```python
# Python 3.9+ 的简化版（无大小限制，要自己控制）
from functools import cache

@cache
def fib(n):
    return n if n < 2 else fib(n-1) + fib(n-2)
```

## 向量化：CPU 密集的正解

:::tip[一个循环 vs 一次 numpy 调用]
```python
# 纯 Python：解释器逐元素循环
total = sum(x * 2 for x in data)

# numpy：在 C 里循环，且能 SIMD
import numpy as np
arr = np.asarray(data)
total = (arr * 2).sum()
```

**差距通常在 10~100 倍** —— 因为 numpy 的循环在 C 层，且能利用 SIMD 指令。

**前提**：数据能装进内存，且操作能表达成数组运算（没有复杂的控制流）。
:::

:::danger[numpy 也有"反模式"]
```python
# ❌ 在 Python 层逐元素访问
for i in range(len(arr)):
    arr[i] = arr[i] * 2

# ✅ 整体运算
arr = arr * 2
```

**Python 层循环访问 numpy 元素比纯 list 还慢**（每次都要装箱成 Python 对象）。
:::

## 什么时候该换语言

:::warning[三个明确信号]
**① 优化到"算法已经最优"还是慢**

如果 `cProfile` 显示时间均匀分布在一堆"已经很合理"的代码里，说明是**解释器开销**本身的问题。

**② 需要处理的数据量超出内存**

Python 的对象开销很大（一个 `int` 约 28 字节）。**几 GB 的数据用 Python 原生结构很难受。**

**③ 有硬实时要求**

GC 停顿、解释器调度都不可控。
:::

:::tip[换语言的正确顺序]
1. **先用 C 扩展 / Cython 只重写热点函数**（保留其余 Python 代码）
2. **或用 `numba` JIT**（加个装饰器就行，但只支持数值代码）
3. 最后才考虑整体重写

**"整体重写"是最贵的方案**，而且往往重写后发现瓶颈其实在数据库。
:::

```python
# numba：装个装饰器就 JIT 编译
from numba import njit

@njit
def loop_heavy(arr):
    s = 0.0
    for x in arr:
        s += x * x
    return s
```

**注意**：`njit` 只支持有限的 Python 子集（不能用 list of str、不能用 dict 的复杂操作）。

## 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 优化后没变快 | 优化了非热点 | 先 `cProfile` 按 `tottime` 排 |
| `cProfile` 显示的时间不合理 | 剖析开销干扰 | 换 `py-spy` 采样 |
| `timeit` 结果跳动大 | `number` 太小 | 加大到秒级 |
| 第二次跑飞快 | 磁盘/CPU 缓存 | 每次重开进程或用不同数据 |
| `lru_cache` 内存暴涨 | `maxsize=None` | 设上限 |
| numpy 比 list 慢 | 在 Python 层逐元素访问 | 整体运算 |
| 多进程没提速 | 数据太大、传输开销 | 用共享内存 / 减少传输 |
| 多线程没提速 | GIL | 改多进程或 C 扩展 |

:::danger[多进程传大数据的开销常被忽略]
**`multiprocessing` 把参数和返回值都要 pickle 序列化并通过管道传输。**

**传一个 100MB 的数组给 8 个进程 → 序列化 + 传输可能比计算本身还慢。**

**解法**：用 `multiprocessing.shared_memory`，或让每个进程自己读文件。
:::
