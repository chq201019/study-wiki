# GDB 调试实战

**本课目标**：从"加 printf"升级到"用调试器看清现场"。

## 编译时必须加 `-g`

```bash
gcc -g -O0 main.c -o app          # 调试用
gcc -g -O2 main.c -o app          # 优化 + 调试信息（行号可能不准）
```

:::warning[`-g` 不能省，但 `-O0` 不是必须]
**`-g` 产生调试符号**（变量名、行号、类型）。

**`-O2` 也能加 `-g`**，但会出现：

- 变量被优化掉（`<optimized out>`）
- 行号跳跃
- 函数被内联，栈帧缺失

**建议**：开发期 `-O0 -g`，复现性能问题时 `-O2 -g` 并接受部分信息缺失。
:::

## 最小可用流程

```bash
gdb ./app
```

```gdb
(gdb) run                 # 运行（可带参数：run arg1 arg2）
(gdb) break main          # 在 main 打断点
(gdb) break foo.c:42      # 在文件第 42 行
(gdb) break foo           # 在函数 foo
(gdb) next                # 下一行（不进入函数）
(gdb) step                # 下一行（进入函数）
(gdb) finish              # 执行到当前函数返回
(gdb) continue            # 继续到下一个断点
(gdb) print x             # 打印变量
(gdb) print *ptr          # 打印指针指向的内容
(gdb) bt                  # 调用栈（backtrace）
(gdb) frame 2             # 切到第 2 层栈帧
(gdb) info locals         # 当前帧所有局部变量
(gdb) quit
```

:::tip[`bt` + `frame` 是最核心的组合]
```gdb
(gdb) bt
# #0  parse_config (path=0x0) at config.c:88
# #1  init_app () at main.c:42
# #2  main () at main.c:120

(gdb) frame 0
(gdb) info locals        # 看 parse_config 里的变量
```

**崩溃时第一件事永远是 `bt`** —— 它告诉你"谁调用了谁"。
:::

## 条件断点与观察点

```gdb
(gdb) break process if i == 500        # 只在 i==500 时停
(gdb) condition 2 ptr == NULL          # 给已存在的断点加条件
(gdb) ignore 1 1000                    # 断点 1 忽略前 1000 次

(gdb) watch counter                    # 变量被写时停（观察点）
(gdb) rwatch counter                   # 被读时停
(gdb) awatch counter                   # 读写都停
```

:::danger[观察点数量有限（硬件断点）]
**`watch` 底层用硬件断点，x86 通常只有 4 个。**

**超了会报 `Hardware watchpoint ... cannot be inserted`。**

**这时**：改成软件观察点（`set can-use-hw-watchpoints 0`，慢很多），或换用断点。

**`watch` 是排查"变量莫名被改"的终极武器** —— 一设就知道是谁改的（`bt` 看一眼）。
:::

:::tip[条件断点比"手动 continue 一千次"快得多]
```gdb
# ❌ 手动
(gdb) continue      # 按 1000 次...

# ✅ 条件断点
(gdb) break loop_body if i == 999
```

**注意**：GDB 每到达一次断点都会求值条件式，**循环百万次时条件断点也会很慢**。

**更快的方法**：把条件写进代码 `if (i == 999) { volatile int stop = 0; /* 在这打断点 */ }`。
:::

## Core Dump：事后还原现场

```bash
ulimit -c unlimited                    # 允许生成 core（当前 shell 有效）
cat /proc/sys/kernel/core_pattern      # 看 core 存哪

gdb ./app core                         # 加载 core
```

:::warning[`ulimit -c` 只对当前 shell 有效]
```bash
ulimit -c unlimited && ./app           # ✅ 同一条命令里
```

**在 systemd 服务里要配**：

```ini
[Service]
LimitCORE=infinity
```
:::

```gdb
(gdb) bt                    # 崩溃时的调用栈
(gdb) info registers        # 寄存器值
(gdb) frame 0
(gdb) info locals
(gdb) list                  # 看源码上下文
(gdb) print $_siginfo       # 信号详情（如段错误的地址）
```

:::danger[core 里的信息是"那一刻的快照"]
**加载 core 时不能用 `run`** —— 程序已经死了，你只能看，不能动。

**能做的**：看栈、看变量、看寄存器。**不能做的**：单步执行、修改再继续。

**如果 core 里全是 `??`** → 二进制和 core 不匹配（重新编译过）或没带 `-g`。
:::

## 多线程调试

```gdb
(gdb) info threads                  # 列出所有线程
(gdb) thread 3                      # 切到线程 3
(gdb) thread apply all bt           # 所有线程的栈（死锁排查必用！）
(gdb) break foo thread 2            # 只在 2 号线程命中
```

:::tip[死锁排查的标准动作]
```gdb
(gdb) thread apply all bt
```

**然后看每个线程是否卡在 `pthread_mutex_lock` / `__lll_lock_wait`** —— 如果两个线程分别持有对方要的锁，就是死锁。

**这是排查死锁最快的办法**，比任何日志都快。
:::

## 修改程序状态

```gdb
(gdb) set var x = 100              # 改变量值
(gdb) set var flag = 1             # 强制走某个分支
(gdb) jump 42                      # 跳到第 42 行
(gdb) return 0                     # 从当前函数直接返回 0
(gdb) call printf("%d\n", x)       # 调用函数（有风险）
```

:::danger[`call` 在优化过的代码里不可靠]
**被内联/优化掉的函数调不到**，甚至可能破坏目标进程状态。

**而且 `call` 会让程序实际执行** —— 如果那个函数有副作用（写文件、发网络包），就真的发生了。
:::

:::tip[`set var` 是复现 bug 的最快方式]
```gdb
# 假设 bug 只在某种边界输入下出现
(gdb) break validate
(gdb) run
(gdb) set var input_len = 0        # 直接构造边界条件
(gdb) continue
```

**不用改代码、不用重编、不用构造真实输入。**
:::

## 十个省时间的技巧

| 技巧 | 命令 |
| --- | --- |
| **看宏的值** | `print (int)SOME_MACRO` 或 `info macro SOME_MACRO` |
| **打印数组** | `print arr[0]@10`（打印前 10 个元素） |
| **打印结构体全部** | `set print pretty on` 然后 `print *p` |
| **看内存** | `x/16xb ptr` / `x/4wx ptr` |
| **反汇编当前位置** | `disassemble /m`（带源码混排） |
| **保存断点** | `save breakpoints file` / `source file` |
| **记录日志** | `set logging on`（输出同时写入 gdb.txt） |
| **粘贴代码到 shell** | `shell ls -la` |
| **看调用者变量** | `frame 1` 然后 `print param` |
| **重复上条命令** | 直接回车 |

```gdb
(gdb) print arr[0]@5
$1 = {1, 2, 3, 4, 5}          # 数组切片，非常好用

(gdb) print *stu
$2 = {
  name = "张三",
  age = 20
}
```

:::warning[`x` 命令的格式容易记错]
```text
x/<数量><格式><单位> 地址

格式：x=十六进制 d=十进制 u=无符号 o=八进制 t=二进制 c=字符 s=字符串
单位：b=字节 h=半字 w=字 g=巨字
```

```gdb
(gdb) x/16xb ptr         # 16 个字节，十六进制
(gdb) x/4dw arr          # 4 个 32 位十进制
(gdb) x/s str            # 当字符串看
```
:::

## 非交互式与批量

```bash
# 一次性执行多条命令（CI 里有用）
gdb -batch -ex "run" -ex "bt" -ex "quit" ./app

# 附加到运行中的进程
gdb -p 1234
```

:::danger[`gdb -p` 会暂停目标进程]
**attach 后进程停在原处，直到你 `continue` 或 `detach`。**

```gdb
(gdb) detach        # 放手，让进程继续跑
(gdb) quit
```

**在生产环境 attach 前要清楚：这期间服务是停的。**
:::

## 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 变量显示 `<optimized out>` | `-O2` 优化掉了 | 用 `-O0` 复现 |
| 全是 `??` | 没 `-g` 或二进制不匹配 | 重编带 `-g` |
| 断点设不上 | 代码被内联/优化 | `-O0` 或改在别处 |
| `watch` 报无法插入 | 硬件断点用完 | `set can-use-hw-watchpoints 0` |
| core 不生成 | `ulimit -c` 是 0 | 设置并注意 systemd `LimitCORE` |
| 多线程单步乱跳 | 线程在切换 | `set scheduler-locking on` |
| `next` 跳得很怪 | 优化导致行号错乱 | 同上，用 `-O0` |
| 程序在 gdb 里正常、外面崩 | 未初始化内存恰好是 0 | 这是最难的 bug，见下 |

:::danger["在 gdb 里正常、单独跑就崩"怎么办]
**典型原因**：未初始化的栈变量在 gdb 里恰好是 0（或者地址布局不同掩盖了越界）。

**手段**：

```bash
valgrind --track-origins=yes ./app
gcc -fsanitize=address,undefined -g main.c
```

**ASan/UBSan/Valgrind 比 gdb 更适合抓这类"环境敏感"的内存问题。**
:::

:::tip[`set scheduler-locking on` 让多线程单步可控]
```gdb
(gdb) set scheduler-locking on
```

**只有当前线程会跑，其他线程冻结** —— 单步调试多线程时几乎是必需的。
:::
