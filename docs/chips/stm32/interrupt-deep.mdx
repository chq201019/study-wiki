# 03 中断系统深入

**本课目标**：搞清优先级到底怎么比较，知道临界区该怎么保护。

## Cortex-M3 的异常模型

:::info[中断和异常在 Cortex-M 上是同一个机制]
| 类别 | 编号 | 说明 |
| --- | --- | --- |
| **系统异常** | 1~15 | 复位、NMI、HardFault、SVC、PendSV、SysTick 等 |
| **外部中断（IRQ）** | 16 起 | 外设中断：EXTI、TIM、USART… |

**STM32F103 支持 60 个外部中断**（编号 16~75）。

**"异常"是统称，"中断"通常特指外部 IRQ**——但底层走的是同一套硬件。
:::

### 向量表

```text
Flash 起始地址（0x08000000）就是向量表：
偏移 0x00 : 初始栈顶值（MSP）
偏移 0x04 : Reset_Handler 地址
偏移 0x08 : NMI_Handler
偏移 0x0C : HardFault_Handler
...
偏移 0x40 : 第一个外部中断（EXTI0）
```

:::danger[Bootloader 必须重定位向量表]
如果你的程序不是从 `0x08000000` 启动（比如 Bootloader 在 0x08000000，应用在 0x08010000），**必须改 VTOR**：

```c
SCB->VTOR = 0x08010000;      /* 告诉内核新向量表在哪 */
```

**不改的话，中断会跳到 Bootloader 的向量表里，行为完全错乱。**

（[第 10 课](./advanced-index)细讲。）
:::

## 优先级：4 位，16 级

![NVIC 优先级分组：4 位如何在五种分组下切成抢占位与子优先级位，Group 4 为 16 级抢占](/img/diagrams/stm32-nvic-priority.svg)


:::warning[STM32F103 只实现了 4 位优先级]
Cortex-M3 架构定义了 **8 位**优先级（256 级），但 **STM32F103 只接了 4 位**（16 级）。

```text
优先级寄存器高 4 位有效，低 4 位读回是 0
```

**所以你能用的优先级只有 0~15。**

（F4/H7 也是 4 位，部分型号有更多。）
:::

### 抢占优先级 vs 子优先级

```text
一个 4 位的优先级数字，被"分组"切成两段：

   bits[7:4]
   ┌────┬────┐
   │ 抢占 │ 子  │
   └────┴────┘
```

| 分组 | 抢占位数 | 子优先级位数 | 效果 |
| --- | --- | --- | --- |
| `NVIC_PRIORITYGROUP_0` | 0 | **4** | **完全不能抢占**（全部排队） |
| `NVIC_PRIORITYGROUP_1` | 1 | 3 | 2 级抢占 |
| `NVIC_PRIORITYGROUP_2` | 2 | 2 | 4 级抢占 |
| `NVIC_PRIORITYGROUP_3` | 3 | 1 | 8 级抢占 |
| **`NVIC_PRIORITYGROUP_4`** | **4** | **0** | **16 级抢占（HAL 默认）** |

:::tip[只有一个全局分组设置]
```c
HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_4);    /* 整个系统只设一次 */
```

**分组是全局的，改了会影响所有中断。** 不要在运行中随意改。

**HAL 在 `HAL_Init()` 里已经设成 Group 4**（全抢占，子优先级不起作用）。
:::

:::danger[优先级数字越小越高——和 FreeRTOS 任务相反]
| 场景 | 数字大 | 数字小 |
| --- | --- | --- |
| **NVIC 中断** | 低优先级 | **高优先级** |
| **FreeRTOS 任务** | **高优先级** | 低优先级 |

**这两套规则完全相反，是 STM32 开发中最容易记混的地方。**

**记忆法**：中断是"紧急程度"（0 号最急），任务是"重要性"（数字大的更重要）。
:::

### 抢占的实际含义

```c
/* 定时器中断：抢占优先级 0（最高） */
HAL_NVIC_SetPriority(TIM3_IRQn, 0, 0);

/* 串口中断：抢占优先级 5 */
HAL_NVIC_SetPriority(USART1_IRQn, 5, 0);
```

**执行 USART1 的 ISR 时，如果 TIM3 中断到来 → 立刻打断 USART1，先执行 TIM3。**

**这叫嵌套中断**（`Group 4` 下按数字比较，小的能打断大的）。

:::warning[同级中断不能互相抢占]
**抢占优先级相同的中断，谁先来谁先执行，后来的等着**——即使子优先级不同（Group 4 下子优先级没用）。

**所以想让 A 打断 B，A 的抢占优先级必须严格小于 B。**
:::

## 中断延迟由什么组成

```text
硬件事件发生
   ↓ ① 硬件检测 + 同步（约 2~3 周期）
   ↓ ② 压栈（8 个寄存器，R0-R3/R12/LR/PC/xPSR，约 12 周期）
   ↓ ③ 取向量 + 跳转
   ↓ ④ 你的 ISR 第一条指令
```

:::tip[典型中断延迟约 12~16 个周期]
72MHz 下约 **0.17~0.22 µs**（不含你 ISR 自身耗时）。

**这是硬件保证的上限，不会因为软件写得"重"而变慢**——变慢的是 ④ 之后的部分。

**真正影响响应的是**：

- 当前是否在执行更高优先级的中断（嵌套）
- 是否处于临界区（关中断）
- ISR 写得太长（占了时间）
:::

## 三个硬件"加速"机制

:::tip[Cortex-M 的三种优化，你什么都不用做]
**① 尾链（Tail-chaining）**

ISR 结束时如果还有挂起的中断，**不回主程序，直接进下一个 ISR**。省掉一次出栈+入栈。

**② 迟到（Late-arriving）**

如果正在压栈时来了更高优先级中断，**压栈完成后直接转去执行它**，不用先执行原来的。

**③ 出栈跳过（Pop preemption）**

如果出栈过程中来了中断，**重新入栈并立即处理**。

**这些机制让"连续中断"的开销远小于"每次完整进出"。**
:::

## 临界区：保护共享数据

:::danger[改共享变量时被中断打断会出错]
```c
uint32_t counter = 0;

/* 主循环 */
counter++;      /* 实际是 读 → 加 → 写 三步 */

/* 如果在"读完还没写回"时来了中断，中断里也 counter++ */
/* 结果：两次自增只加了一次 */
```
:::

### 方案一：关全局中断

```c
__disable_irq();            /* 关所有中断（PRIMASK = 1） */
counter++;                  /* 临界区 */
__enable_irq();             /* 开中断 */
```

:::warning[关了要记得开，而且临界区必须短]
```c
__disable_irq();
HAL_Delay(10);              /* ❌ 10ms 内系统失去所有中断响应 */
__enable_irq();
```

**后果**：串口丢数据、定时器计错、看门狗可能复位。

**规矩：临界区只包住必须原子的那几条语句，绝不调任何函数。**
:::

### 方案二：只关部分优先级（BASEPRI）

```c
/* 只屏蔽优先级 ≥ 5 的中断，高优先级的还能响应 */
__set_BASEPRI(5 << (8 - __NVIC_PRIO_BITS));
counter++;
__set_BASEPRI(0);
```

**比关全局精细**，适合"想让高优先级中断还能跑"的场景。

### 方案三：用原子指令

```c
/* 单条指令完成，不需要临界区 */
__disable_irq();   /* 实际上 LDREX/STREX 或专用指令更优 */
```

:::tip[对单个变量自增，用 `__atomic` 或位带]
```c
/* GCC 内建原子操作 */
__atomic_add_fetch(&counter, 1, __ATOMIC_SEQ_CST);
```

**Cortex-M3 没有单指令自增内存**，所以底层还是靠 LDREX/STREX（独占访问）。

**只有单核时，"关中断 + 操作 + 开中断"是最简单可靠的方案。**
:::

## ISR 写多长算"太长"

:::danger[ISR 里绝对不能做的四件事]
| 禁止 | 原因 |
| --- | --- |
| **`HAL_Delay` / `vTaskDelay`** | 中断里不能阻塞；HAL_Delay 依赖 SysTick，而 SysTick 优先级更低 → **死锁** |
| **`printf` / 串口发送** | 阻塞几毫秒，远超合理中断时间 |
| **`malloc` / `free`** | 非中断安全，会破坏堆 |
| **等标志位** | `while(!flag)` 可能永远等不到 |

**违反后果**：丢中断、看门狗复位、随机死机——**而且极难复现**。
:::

:::tip[ISR 该多长]
**经验值：ISR 执行时间控制在 10 µs 以内**（72MHz 下约 720 条指令）。

**超了就该拆分**：

```c
volatile bool flag = false;
volatile uint32_t data = 0;

void TIM2_IRQHandler(void) {
    /* ISR 里只取数据 + 置标志 */
    data = TIM2->CNT;
    flag = true;
    /* 清中断标志 */
    TIM2->SR &= ~TIM_SR_UIF;
}

/* 主循环处理 */
if (flag) {
    flag = false;
    process(data);          /* 耗时的活在这里做 */
}
```

**记住：ISR 只做"必须立刻做"的事，其余推给主循环或任务。**
:::

## 中断优先级的实用配置

:::tip[一套可以直接抄的优先级规划]
| 中断 | 抢占优先级 | 理由 |
| --- | --- | --- |
| **SysTick / FreeRTOS 时基** | **15（最低）** | 要能被所有业务中断打断 |
| 看门狗 | 0（最高） | 必须能及时响应 |
| 电机控制 / 编码器 | 1~2 | 硬实时 |
| 串口 / SPI 收发 | 5~6 | 要及时搬数据 |
| 按键 / 慢速传感器 | 8~10 | 不着急 |
| 定时器周期任务 | 7 | 中等 |

**关键点：SysTick 一定要设成最低**。

HAL 默认给了它较低优先级（通常是 15），**如果你手动调高了，`HAL_Delay` 会打断业务中断**，叠加出奇怪问题。
:::

:::danger[FreeRTOS 的特殊要求]
用 FreeRTOS 时：

```c
/* 所有调用 FromISR API 的中断，优先级必须 ≥ configMAX_SYSCALL_INTERRUPT_PRIORITY */
```

**具体数值取决于 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` 配置。**

**优先级比它高的中断，不能用 `FromISR` 系列 API**——否则会破坏内核状态。

（[第 15 课](./advanced-index)细讲。）
:::

## 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 中断一次都不进 | NVIC 没使能 | `HAL_NVIC_EnableIRQ(irq)` |
| 只进一次 | ISR 没清标志 | 清 SR 寄存器 |
| 高优先级不抢占 | 分组设成全排队 | `SetPriorityGrouping(GROUP_4)` |
| ISR 里卡死 | 调了 `HAL_Delay` | 改置标志位 |
| 数据偶发错乱 | 共享变量没保护 | 临界区或 `volatile`+原子 |
| Bootloader 后中断乱跳 | 没设 `SCB->VTOR` | 重定位向量表 |
| 优先级数字搞反 | 和 FreeRTOS 记混 | 中断数字小=高 |

:::warning[`volatile` 解决不了原子性]
```c
volatile uint32_t counter;
counter++;      /* volatile 只保证"每次真读内存"，不保证三步不被插入 */
```

**`volatile` 管的是"编译器别优化"，不是"别被中断打断"。**

**要原子性必须用临界区或原子指令。**
:::
