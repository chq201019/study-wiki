# 测试策略与分层

**本课目标**：用最少的测试覆盖最多的风险。

## 三层测试

| 层 | 测什么 | 速度 | 稳定性 |
| --- | --- | --- | --- |
| **单元** | 一个函数/类，依赖全 mock | 毫秒 | 高 |
| **集成** | 多个模块 + 真实数据库/网络 | 秒 | 中 |
| **端到端** | 完整流程（起服务、发请求） | 十秒 | **低（易 flaky）** |

:::info[测试金字塔 vs 实际]
**理论**：大量单元 + 少量集成 + 极少 e2e。

**实际**：很多团队变成"冰淇淋筒"（大量 e2e，很少单元）—— 因为 e2e 写起来直观。

**后果**：测试跑一次十几分钟、经常 flaky、失败时不知道哪里错。
:::

:::warning[我推荐的现实比例]
```text
单元测试    50%  ← 纯逻辑、边界、错误路径
集成测试    40%  ← 数据库、外部服务、序列化
端到端      10%  ← 只覆盖关键用户路径
```

**集成测试占比高是合理的** —— 真实 bug 大多在"模块之间的接缝"上。
:::

## 什么该测

:::tip[按风险排序]
**高价值**：

- **边界条件**（空、单元素、最大、负数）
- **错误路径**（超时、失败、非法输入）
- **曾经出过 bug 的地方**（回归测试）
- **复杂纯逻辑**（解析、算法、状态机）
- **金额/计数/权限**（错了代价大）

**低价值**：

- getter/setter
- 框架本身的行为
- 实现细节（"调用了 3 次 helper"）
- UI 的具体像素
:::

:::danger[不要测实现细节]
```python
def test_process():
    with patch("mod.helper") as h:
        process()
        assert h.call_count == 3      # 错：重构就废
```

**这个测试锁定的是"实现方式"，不是"行为契约"。**

**改测**：`assert process(input) == expected_output`。
:::

## 让测试跑得快

:::danger[测试慢的三个原因]
1. **每个测试都建真实数据库/网络连接**
2. **有 `sleep` 等待**
3. **测试之间没有隔离，只能串行跑**
:::

```python
# 慢：每个测试建一次库
def test_a():
    db = create_database()      # 2 秒
    ...

# 快：用事务回滚做隔离
@pytest.fixture
def db():
    conn = connect()            # 整个会话一次
    trans = conn.begin()
    yield conn
    trans.rollback()            # 每个测试后回滚
```

:::tip[三个提速手段]
**① 事务回滚代替重建**（数据库测试）

**② 注入时钟而不是 sleep**
```python
def test_timeout(clock):
    clock.advance(10)           # 瞬间"过了 10 秒"
```

**③ 并行跑**：`pytest -n auto`（pytest-xdist）
:::

## flaky 测试的六种来源

| 来源 | 表现 | 解决 |
| --- | --- | --- |
| **共享状态** | 单独跑过、一起跑挂 | fixture 用 function 作用域 |
| **依赖时间** | 随机失败 | 注入时钟 |
| **依赖顺序** | 打乱就挂 | `pytest-randomly` 暴露 |
| **依赖网络** | 时快时慢 | mock 掉 |
| **并发竞态** | 偶发 | 加同步或串行 |
| **浮点比较** | 偶尔不等 | 用误差范围 |

:::danger[flaky 测试的代价被严重低估]
**一旦团队习惯"这个测试经常挂，重跑一下就好"** —— 所有测试的可信度都归零。

**规矩**：**flaky 测试必须在 24 小时内修复或删除**，不能无限重跑。
:::

## 覆盖率该怎么看

:::warning[覆盖率是"下限检查"而不是"质量指标"]
```python
def test_useless():
    add(1, 2)          # 覆盖率 100%，但没有任何断言
```

**这行代码覆盖率算满，但什么都没验证。**
:::

**更有价值的指标**：

- 关键路径是否都有断言
- **错误路径是否覆盖**（很多团队覆盖率 80% 但错误路径 0%）
- 是否有回归测试
- **mutation testing**（改坏代码看测试能不能发现）

## 测试的组织

```text
tests/
├── unit/            # 快，无 IO
│   ├── test_parser.py
│   └── test_calc.py
├── integration/     # 需要数据库/网络
│   └── test_repo.py
└── e2e/             # 完整流程
    └── test_flow.py
```

```bash
pytest tests/unit            # 开发时只跑快的
pytest                      # CI 跑全部
pytest -m "not slow"        # 用标记跳过慢测试
```

## 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 测试跑 10 分钟 | 大量 e2e | 改金字塔比例 |
| 经常 flaky | 依赖时间/网络/顺序 | 注入时钟、mock、隔离 |
| 覆盖率 90% 还出 bug | 只测了 happy path | 补错误路径 |
| 重构就要改测试 | 测了实现细节 | 改测行为 |
| 不知道哪里错了 | e2e 失败信息模糊 | 加单元测试定位 |
| CI 上挂本地过 | 时区/路径/locale | 显式指定 |

:::tip[测试也要能"故意失败"]
**定期故意改坏一处代码，确认测试真的会红。**

**很多"通过"的测试其实什么都没测** —— 一次 mutation 检查就能暴露。
:::
