# 配置与密钥管理

**本课目标**：让密钥不出现在 git、日志、进程列表里。

## 三种错误做法

:::danger[① 写死在源码里]
```python
DB_PASSWORD = "hunter2"          # ❌ 提交到 git 就永久泄露
```

**即使后来删掉，git 历史里还在** —— 任何人 clone 都能翻出来。
:::

:::danger[② 通过命令行参数传]
```bash
mysql --password=hunter2          # ❌ 出现在 ps 输出和 shell 历史里
```

**同一台机器的任何用户都能 `ps aux` 看到。**
:::

:::danger[③ 存在日志里]
```python
logger.info(f"connecting with password={pwd}")   # ❌
```

**日志经常被同步到第三方、打包发给支持人员。**
:::

## `.env` + 环境变量：最小可用方案

```bash
# .env（必须加进 .gitignore）
DB_HOST=localhost
DB_PASSWORD=s3cr3t
API_KEY=abc123
```

```python
# 用 python-dotenv
from dotenv import load_dotenv
import os

load_dotenv()                          # 只在开发时读 .env
pwd = os.environ["DB_PASSWORD"]        # 生产由 systemd/容器注入
```

:::danger[`.env` 必须进 `.gitignore`，而且要检查历史]
```bash
echo ".env" >> .gitignore

# 检查是否已经泄露过
git log --all --full-history -- .env
```

**如果已经提交过，用 `git filter-repo` 清理历史并立即轮换密钥。**
:::

:::warning[创建 `.env` 时先设权限]
```bash
touch .env && chmod 600 .env     # ✅ 先设权限再写内容
```

**反过来写（先写内容再 chmod）会有一小段时间其他用户可读。**
:::

## 环境变量的边界

:::info[环境变量比源码好，但不是银弹]
**能被读到的路径**：

- `/proc/<pid>/environ` —— **同用户可读**（root 可读所有）
- 容器里 `docker inspect` 能看到
- 崩溃转储（core dump）里可能有

**所以环境变量适合"不太敏感"的配置**，真正的密钥应该走专门的机制。
:::

```bash
# 验证一下：环境变量确实能被同用户读到
cat /proc/self/environ | tr "\0" "\n" | grep PASSWORD
```

## 更可靠的方案

| 方案 | 适合 | 特点 |
| --- | --- | --- |
| **文件 + 600 权限** | 单机服务 | 简单，systemd 可配 `LoadCredential` |
| **systemd `LoadCredential`** | Linux 服务 | **密钥不出现在环境变量里** |
| Vault / AWS Secrets Manager | 多机、需要审计 | 动态密钥、自动轮换 |
| 云厂商 IAM 角色 | 云上 | 无需静态密钥 |

```ini
# systemd：把密钥作为文件传给服务，而不是环境变量
[Service]
LoadCredential=dbpass:/etc/myapp/dbpass
ExecStart=/usr/local/bin/myapp
```

```python
# 服务里从 $CREDENTIALS_DIRECTORY 读
import os, pathlib
p = pathlib.Path(os.environ["CREDENTIALS_DIRECTORY"]) / "dbpass"
pwd = p.read_text().strip()
```

:::tip[`LoadCredential` 好在哪]
- **密钥不出现在 `environ` 里**（避免 `/proc` 泄露）
- **不出现在 `ps` 里**
- systemd 自动管理临时文件的权限与生命周期
:::

## 最小权限

:::danger[一个密钥干所有事是最常见的错误]
```text
❌ 一个 root 数据库账号给所有服务用
✅ 每个服务一个账号，只授权它需要的表
```

**具体做法**：

```sql
CREATE USER app_readonly IDENTIFIED BY "...";
GRANT SELECT ON appdb.* TO app_readonly;

CREATE USER app_writer IDENTIFIED BY "...";
GRANT SELECT, INSERT, UPDATE ON appdb.orders TO app_writer;
```
:::

**API 密钥也一样**：读密钥和写密钥分开，限制来源 IP、限制调用配额。

## 轮换

:::warning[设计时就要能轮换]
**如果更换密钥需要停机改代码，那你就永远不会去换它。**

**要做到**：

1. 密钥从配置读（不是硬编码）
2. 支持**同时存在新旧两个密钥**（滚动切换）
3. 有明确的轮换周期（90 天是常见标准）
:::

```python
# 支持多密钥验证（轮换期间新旧都有效）
VALID_KEYS = {k.strip() for k in os.environ["API_KEYS"].split(",")}

def verify(token):
    return token in VALID_KEYS
```

## 泄露后的应急

:::danger[发现泄露后的正确顺序]
1. **立即轮换/吊销那个密钥**（先止血，别急着查原因）
2. 检查使用记录（有没有被滥用）
3. 清理 git 历史（`git filter-repo`）
4. 排查泄露路径（日志？公开仓库？截图？）
5. 复盘：为什么密钥能被拿走
:::

:::warning[清理 git 历史不会让已泄露的密钥变安全]
**别人可能早就 clone 了。**

**所以第 1 步永远是轮换，不是清理。**
:::

## 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 密钥进了 git | 没 `.gitignore` | 加忽略 + 清理历史 + 轮换 |
| `ps` 能看到密码 | 命令行传参 | 改用配置文件/环境变量 |
| 日志里有密钥 | 打印了配置对象 | 敏感字段脱敏 |
| 容器 `inspect` 能看到 | 用 `-e` 传 | 用 secret 挂载 |
| 换密钥要停机 | 硬编码 | 改成配置读取 |
| 一个密钥全权限 | 图省事 | 分账号 + 最小权限 |
| `.env` 权限过宽 | 默认 644 | `chmod 600` |

:::tip[打印配置时先脱敏]
```python
SENSITIVE = {"password", "token", "key", "secret"}

def mask(d):
    return {k: ("***" if any(s in k.lower() for s in SENSITIVE) else v)
            for k, v in d.items()}
```

**这条能挡住 90% 的"日志泄露"事故。**
:::
